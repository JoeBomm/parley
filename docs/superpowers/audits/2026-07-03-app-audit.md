## A. Architecture / correctness

### A1. 🔴 `stop` blocks on the whole pipeline (the root of the "no processing state" gap)
`MeetingManager.stop()` awaits `finalize` (transcribe + summarize + post), which on CPU
whisper can take minutes. Consequences:

- `POST /guilds/:g/live/:channelId/stop` hangs for the whole pipeline; the dashboard
  Stop button spins "Stopping…" for minutes.
- `/leave` in Discord edits its reply only after the full pipeline.
- The session is removed from `manager.active` at the *start* of `stop()`, so the Live
  page shows "Nothing recording" the entire time the meeting is actually processing.
  This is exactly the missing "Processing" state.

Fix: decouple. Stop capture + destroy the voice connection synchronously, mark the
meeting `processing`, return immediately, run the pipeline in the background (fire and
forget with the existing failure handling). See the companion plan doc.

### A2. 🔴 One bad track fails the whole transcription
`transcribeTracks` throws on the first failed track → status `transcription_failed`,
all successfully transcribed tracks discarded (utterances are only inserted after the
loop completes in the orchestrator). A single corrupt PCM or one STT hiccup loses the
whole meeting. Fix: per-track try/catch, keep partial results, record failed-track count
and surface it in the notes/status.

### A3. 🟡 No recovery when the voice connection dies mid-meeting
`connection.on('stateChange')` only logs. If the bot is force-disconnected (admin kick,
region move, network drop), the session stays in `manager.active` forever: Live shows a
phantom recording, audio stops being captured, and nothing finalizes. Fix: listen for
`VoiceConnectionStatus.Disconnected`/`Destroyed` (with the standard 5s reconnect grace
from @discordjs/voice docs) and finalize the meeting.

### A4. 🟡 `ended_at` is set at `done`, not when recording stops
`db.setMeetingStatus(id, 'done', now)` stamps `ended_at` after processing, so every
meeting's duration (`fmtDuration(started_at, ended_at)`) silently includes transcription
+ summarization time. Stamp `ended_at` when capture stops instead. (Also gives the
Live "Processing" card a correct "recorded Xm" figure.)

### A5. 🟡 `joiningInProgress` can leak a key
In `joinAndStart`, if `manager.start(...)` or the attendee mapping throws after
`entersState` succeeds, the joinKey is never deleted → that channel can never be
auto-joined again until restart. Wrap the body in try/finally.

### A6. 🟡 Retry races with an active processing run
`RETRYABLE_STATUSES` includes `processing` and `recording`. A user clicking Retry on a
meeting that is *actively* processing (not stuck) double-runs the pipeline (double
Discord post, wasted STT). Once A1 lands, the API can consult the bot's in-flight set
and reject retry for genuinely-active meetings.

### A7. 🔵 Decoder teardown may drop tail audio
`end()` in `attachCapture` calls `out.end()` and immediately destroys the decoder;
frames buffered in the opus decoder pipe may not flush. Prefer ending the source and
letting the pipe drain (`opusStream.destroy()` last, after `out` finishes).

## B. STT sidecar

### B1. 🔴 `async def transcribe` blocks the event loop
`stt_sidecar/server.py` declares the endpoint `async def` but calls the synchronous
`model.transcribe(...)` + iterates segments inline. The entire FastAPI event loop is
blocked during transcription: `/health` stalls (dashboard sidecar status shows it as
down/hung), concurrent requests serialize badly. Fix: make it a plain `def` (FastAPI
runs sync endpoints in a threadpool) or `run_in_executor`.

### B2. 🔴 Hard-coded `device="cpu"` on a machine with an RTX 4070
`WhisperModel(name, device="cpu", compute_type="int8")`. CUDA + float16 is typically
5–15x faster for faster-whisper. Fix: `STT_DEVICE` / `STT_COMPUTE` env vars with
auto-detect (`cuda` if available, else cpu/int8). This is the single biggest raw-speed
lever for the local path.

### B3. 🔵 No batched inference
faster-whisper's `BatchedInferencePipeline` gives a further ~2-4x on GPU for longer
clips. Optional flag once B2 lands.

## C. Pipeline speed (see plan doc for the full speed-up plan)

- 🔴 Tracks are transcribed strictly sequentially (`for … await` in `transcribeTracks`).
  Cloud STT (OpenAI) would be ~Nx faster with a small concurrency pool (4–6). For the
  sidecar, concurrency 2 still overlaps upload/IO with compute.
- 🟡 ffmpeg is spawned per track just to prepend a WAV header. The PCM is already
  s16le/16k/mono; a WAV file is that data plus a 44-byte header. Writing the header in
  JS removes one process spawn per track and the ffmpeg dependency from the hot path.
- 🟡 Everything waits for meeting end. Long-term: transcribe each speaking turn as it
  finishes (registry `finish` → enqueue), so meeting end only needs the summarizer.
  Also unlocks a live transcript in the Live page later.

## D. Web / API

### D1. 🟡 Session cookie never gets the `Secure` attribute
`setSessionCookie` has a comment claiming "Secure only over https" but never appends
`Secure`. Behind a TLS proxy the cookie is still sent over plain http if anything
downgrades. Fix: append `Secure` when `req.secure` (trust proxy is already on).

### D2. 🟡 No login rate limiting
`/api/auth/login` allows unlimited brute force; scrypt slows each attempt (~100ms) but
add a simple in-memory per-IP/per-username backoff (no dep needed).

### D3. 🟡 Non-admin users have full power
Any authenticated user can rewrite provider API keys, Discord credentials, restart the
bot, delete/merge meetings. Only `/api/users` is admin-gated. Decide: either document
"all users are operators", or gate `/system/*`, `/providers/*/key`, and destructive
meeting ops behind `requireAdmin`.

### D4. 🔵 Merge + long endpoints hold the request open
`/meetings/:id/merge` and `/meetings/:id/retry` await the summarizer inline. Acceptable
for now (summaries are seconds, not minutes), but retry with `retranscribe` can be
minutes on CPU — same decoupling pattern as A1 applies eventually.

### D5. 🔵 Live poll runs while tab is hidden
`LiveProvider` polls every 4s forever. Pause on `document.visibilitychange` to cut
noise, and drop to a slower interval when nothing is live or processing.

## E. Data layer

### E1. 🟡 Missing index on `utterances(meeting_id)`
`listUtterances`, the per-row counts in `listRecentRich`, and FTS joins all filter by
`meeting_id` with no index (only the FTS content table rowid). One line:
`CREATE INDEX IF NOT EXISTS utterances_meeting ON utterances(meeting_id)`.
Same for `todos(meeting_id)` / `todos(guild_id)`.

### E2. 🔵 `listRecentRich` N+1 attendee query
A per-row `SELECT display_name FROM attendees …` inside a JS loop. Fine at 100 rows;
fold into one grouped query if meeting lists grow.

### E3. 🔵 Migration reads `PRAGMA table_info` once, then checks three columns
Works, but the `cols` snapshot is taken before any ALTER runs — if a future migration
adds two interdependent columns this pattern breaks. Re-read per check or switch to a
tiny `user_version`-based migration ladder.
